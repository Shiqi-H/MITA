\section{Project Concept}
\subsection{Overview}
Botanical Garden is a browser-based botanical garden that combines \textbf{immersive panoramic exploration} with a \textbf{conversational, voice-driven assistant}. Users move through 360\textdegree{} garden scenes, look at or select 3D plant models, and ask natural-language questions.
The goal is to turn a static botanical exhibit into a fluid multimodal
experience where visual context, plant selection, speech input, adaptive
information panels and TTS feedback work together.

\subsection{Characterizing Features}
\begin{itemize}
    \item \textbf{Immersive 3D environment.} The prototype renders linked
    360\textdegree{} panoramic garden scenes with navigation
    portals and 3D plant models. This gives users a spatial
    context for exploration.

    \item \textbf{Multimodal input.} The system combines visual context,
    plant selection, typed input, speech-to-text via the Web
    Speech API, and click/touch fallback controls. Users can therefore
    interact by looking, selecting, speaking, typing, or clicking overlay
    options depending on the situation.

    \item \textbf{Multimodal output.} Responses are presented through a
    coordinated combination of 3D plant highlights, adaptive 2D information
    panels (botanical, medicinal, comparison and fallback), and text-to-speech
    narration.

    \item \textbf{LLM-assisted dialogue with local fallback.} A lightweight
    stateless backend provides JSON endpoints for intent parsing, information
    generation, disambiguation prompts and comparison speech. The prototype
    first attempts LLM-assisted generation when enabled, but keeps local
    deterministic parsing and structured plant data as fallback so that the
    core interaction does not break when the LLM is unavailable.

    \item \textbf{Referential ambiguity handling.} When the user asks an
    ambiguous question such as \emph{``what is this''} while multiple plants
    are visible or otherwise plausible in the current scene, the system enters
    a referential ambiguity flow. Candidate plants are labelled
    A\,/\,B\,/\,C and can be resolved by clicking, typing, or speaking a
    letter or plant name, with retry guidance and direct-click fallback.

    \item \textbf{Contextual comparison.} The system remembers recently
    visited plants and can compare the current selection with a named plant,
    a previously visited plant, or a plant found in the global database. In
    the current prototype, comparison focuses on drought tolerance while the
    panel also shows supporting attributes where available.
\end{itemize}

\subsection{Target Users and Why It Is Multimodal}
The system targets \textbf{botanical garden visitors, botany students and users who are unable to visit in person} exploring a botanical collection on desktop. Instead of reading long static labels, users can ask focused questions about the plant in front of them.

Botanical Garden is multimodal \textbf{by design}: users interact through
multiple input modalities, including visual context, click/raycast selection,
typed text and speech input, while the system responds through multiple output
modalities, including 3D spatial highlights, visual information cards and
spoken TTS feedback. 

\section{Main Tasks}
This document defines the three main interaction tasks used for heuristic
evaluation of the Botanical Garden prototype.

\subsection{Task 1 - Visual Detection and Multimodal Disambiguation}
\tasksub{Goal.} The user wants to identify a plant using an ambiguous
deictic question such as \emph{``what is this''} or \emph{``what plant am I
looking at?''}. The task evaluates whether the system can detect that the
reference is unclear and guide the user to the intended plant.

\tasksub{Modalities.} \emph{Input:} current camera view, speech-to-text,
typed text, and click/touch selection on the A\,/\,B\,/\,C overlay.
\emph{Output:} candidate highlights in the 3D scene, labelled overlay
options, information panel, and TTS feedback.

\tasksub{Flow.}
\begin{enumerate}
    \item The user asks an ambiguous identification question, for example
    \emph{``what is this''} or \emph{``what plant am I looking at?''}.
    \item If no plant is already selected, the frontend checks the plants in
    the current visual field. When multiple visible plants are detected, the
    system enters a referential ambiguity flow. If visibility detection cannot
    determine a single clear target and the current scene contains multiple
    candidate plants, the scene candidates are used as a fallback ambiguity
    set.
    \item The system generates A\,/\,B\,/\,C labels for the candidate plants,
    highlights them in the 3D scene, and displays a clarification overlay.
    A backend LLM call may be used to produce a natural clarification prompt;
    if this fails, a local prompt is used.
    \item The user resolves the ambiguity by clicking one candidate, typing a
    letter, speaking a letter, or saying the plant name.
    \item If the answer cannot be matched, the system asks the user to choose
    again. After repeated failures, it guides the user toward directly
    clicking the intended target.
    \item Once a candidate is resolved, the selected plant is highlighted and
    its information card is shown.
\end{enumerate}

\tasksub{Success criteria.} Ambiguity is triggered when the user uses an
unclear reference and more than one plant is visible or otherwise plausible in
the current scene; every candidate is clearly labelled; clicking, typing, and
voice-based letter selection work; failure cases provide a retry path and a
direct-click fallback; no plant-specific information card appears before the
target is resolved.

\subsection{Task 2 - Plant Selection and In-depth Dialogue}
\tasksub{Goal.} The user selects one plant and asks targeted follow-up
questions about its properties, such as basic botanical information or
medicinal value. The task evaluates whether the system keeps the selected
plant in context and presents the right type of information panel.

\tasksub{Modalities.} \emph{Input:} plant selection by click/raycast, speech
or typed natural-language query, and fallback buttons for supported topics.
\emph{Output:} selected-plant highlight, botanical or medicinal information
panel, fallback panel for unsupported interests, and TTS narration.

\tasksub{Flow.}
\begin{enumerate}
    \item The user selects a plant directly, or resolves Task~1 ambiguity so
    that one plant becomes the current selection.
    \item The user asks a property question, for example
    \emph{``what is its medicinal value?''}, \emph{``tell me about this
    plant''}, or \emph{``what is it used for?''}.
    \item The frontend parses the intent and topic of interest. For medicinal
    value, medical, or herbal-use questions, the system opens the dedicated
    medicinal information panel.
    \item For supported botanical queries, the system displays the general
    plant information card. Information generation first attempts to use the
    backend LLM endpoint; if generation fails or is disabled, the UI still
    falls back to structured local plant data.
    \item If the user asks for an unsupported interest, such as a topic not
    available in the current prototype, the system shows a fallback interaction
    that guides the user toward supported topics such as botanical features or
    medicinal value.
    \item Subsequent follow-up turns remain attached to the selected plant
    until the user selects another plant or closes the plant panel.
\end{enumerate}

\tasksub{Success criteria.} The selected plant remains visually highlighted;
medicinal questions open the medicinal panel; general botanical questions open
the standard information card; unsupported interests do not dead-end but offer
supported alternatives; local fallback prevents the core interaction from
breaking when LLM generation is unavailable.

\subsection{Task 3 - Contextual Plant Comparison}
\tasksub{Goal.} The user compares the currently selected plant with another
plant mentioned by name or inferred from visit history. For example:

\begin{quote}
\texttt{Is this more drought tolerant than the ficus?}
\end{quote}

\tasksub{Flow.}
\begin{enumerate}
    \item The user has a current plant selected and asks a comparison question,
    such as \emph{``Is this more drought tolerant than the ficus?''} or
    \emph{``compare it with the previous plant''}.
    \item The frontend parses the comparison intent and resolves the second
    plant. It first checks explicit plant names and aliases, then uses the
    user's visited plant history for references such as \emph{``the previous
    one''}. If the target was not visited but exists in the plant database, it
    can still be used as a global database fallback.
    \item The comparison view displays both plant descriptions and key
    attributes, including drought tolerance, height, lifespan, and medicinal
    value where available.
    \item The frontend sends both resolved plant records to the backend
    \texttt{/api/compare} endpoint when LLM comparison speech is enabled.
    The backend is responsible for generating a natural-language comparison
    answer, while the frontend remains responsible for rendering the
    structured side-by-side result.
    \item If no valid comparison target can be resolved, the system explains
    the problem and asks the user to select another plant or use a known plant
    name.
\end{enumerate}

\tasksub{Success criteria.} The system resolves comparison targets from
explicit names, aliases, recent history, or the global plant database; the
comparison panel shows both plants in a structured layout; drought tolerance
is compared clearly in the current prototype; missing targets produce a useful
error instead of a silent failure; the spoken summary and visual comparison
remain consistent.

\section{Prototype Architecture}
\subsection{Architectural Overview}

Botanical Garden is implemented as a browser-based prototype with a lightweight local
backend. The frontend provides the immersive garden experience, plant
selection, speech interaction, visual feedback, and information panels. The
backend provides optional LLM-assisted intent parsing and response generation,
while the frontend keeps a deterministic local fallback so that the main
interaction loop can still work when the LLM service is unavailable.

At a high level, the prototype is divided into four layers:

\begin{enumerate}[label=\arabic*.]

    \item \textbf{Immersive scene layer:} renders the panoramic garden, 3D plant
    models, and spatial highlights.

    \item \textbf{Interaction layer:} captures pointer-based plant selection,
    typed input, speech-to-text input, visible-plant ambiguity detection, and
    ambiguity-resolution actions.

    \item \textbf{Dialogue and grounding layer:} maps user utterances to intents,
    connects those intents to the currently selected plant or recently visited
    plants, and decides which UI response should be shown.

    \item \textbf{Knowledge and generation layer:} stores structured plant
    records and, when enabled, uses the backend LLM service to generate more
    natural spoken explanations.
\end{enumerate}

The architecture intentionally keeps the most important interaction state on
the client side. This makes the prototype responsive and allows plant
selection, local intent parsing, panel rendering, and fallback behavior to work
without a persistent server session.

\subsection{Frontend Architecture}

The frontend is a Vite application written in modular JavaScript. The entry
point is \texttt{src/main.js}, which initializes global UI controls, speech
recognition, plant selection, scene navigation, and the first garden scene.

The main frontend modules are:

\begin{itemize}
    \item \texttt{src/scene/*}: renders the 360-degree garden scenes, 3D plant
    models, and plant selection in the immersive scene.

    \item \texttt{src/app/*}: owns interaction state and high-level behavior
    such as identifying a plant, querying an attribute, comparing plants, and
    resolving ambiguity.

    \item \texttt{src/intent/*}: parses user utterances locally and optionally
    delegates to the backend intent API.

    \item \texttt{src/ui/*}: renders the plant information panel, medical panel,
    comparison panel, fallback panel, ambiguity overlay, and query controls.

    \item \texttt{src/speech/speech.js}: integrates browser speech recognition
    and text-to-speech output.

    \item \texttt{src/data/*}: contains local scene, plant, and intent data used
    by the prototype.
\end{itemize}

The frontend state is centralized in \texttt{src/app/state.js}. It tracks the
active panoramic scene, the currently selected plant, the set of plants currently
visible in the user's view, ambiguity candidates derived from those visible
plants, the ordered list of visited plant ids, and the speech recognition
failure count for retry behavior.

This state is small but important. It allows the system to interpret phrases
such as ``this plant'', ``the previous one'', or ``compare it with lavender''
against the user's actual interaction history instead of treating each
utterance as an isolated command.

\subsection{Backend Architecture}

The backend is a minimal Node.js HTTP server located in \texttt{server/index.js}.
It exposes JSON endpoints that support the frontend dialogue flow:

\begin{itemize}
    \item \texttt{GET /api/health}: health check and configured model information.
    \item \texttt{POST /api/parse-intent}: parses a user utterance into an intent
    and slots.
    \item \texttt{POST /api/generate-info}: generates a spoken answer for one
    plant.
    \item \texttt{POST /api/generate-disambiguation}: generates a clarification
    prompt for multiple candidate plants.
    \item \texttt{POST /api/clarify}: resolves a user's answer to an ambiguity
    prompt.
    \item \texttt{POST /api/compare}: generates a comparison response for two
    plants.
\end{itemize}

The backend is intentionally stateless from the frontend's perspective. Each
request includes the context needed for that turn, such as the utterance,
selected plant, visited plant ids, candidate plants, or dialogue history. This
keeps the prototype simple to run locally and avoids hidden server-side state
that would be hard to debug during evaluation.

The backend services are split by responsibility:

\begin{itemize}
    \item \texttt{server/services/intentParser.js}: deterministic parser fallback.
    \item \texttt{server/services/llm.js}: LLM-backed parsing and response generation.
    \item \texttt{server/services/plantDb.js}: reads the plant database from
    \texttt{src/data/plants.json}.
    \item \texttt{server/handlers/*}: request handlers for query, clarify, and
    compare flows.
\end{itemize}

If the LLM call fails, the server returns a local fallback or an empty generated
speech field. The frontend can still render structured cards from local plant
data, so the visual part of the interaction remains available.

\subsection{Core Interaction Flow}

The most common interaction starts when the user looks at a plant area and asks
a question.

\begin{enumerate}[label=\arabic*.]
    \item The system checks the plants that are currently visible in the user's
    view.
    \item If only one plant is visible or clearly selected, the frontend records
    it as the current plant; if several visible plants could match the user's
    reference, the frontend opens an ambiguity flow.
    \item The user submits text through typing or browser speech recognition.
    \item \texttt{handleQuery()} sends the utterance and current context through
    the intent parser.
    \item The parsed intent is routed to one of the frontend handlers:
    identification, attribute query, comparison, ambiguity resolution, or
    unknown intent.
    \item The selected plant is visually highlighted in the 3D scene.
    \item The corresponding 2D panel is rendered: botanical information,
    medicinal information, comparison result, fallback options, or ambiguity
    choices.
    \item Text-to-speech reads the concise answer or clarification prompt.
\end{enumerate}

For ambiguous references, the frontend stores the visible candidate plants in
state and shows an A/B/C overlay. The user may resolve the ambiguity by clicking
an option or by speaking a phrase such as ``A'' or the plant name. As a fallback
option, users can directly click a plant model to make an explicit selection.

For comparison, the frontend combines the current selected plant with the
visited plant history. This enables contextual queries such as ``Is this more
drought tolerant than the previous one?'' The comparison handler resolves the
second plant, chooses the relevant attribute, and renders a side-by-side
comparison panel.

\subsection{Data Model and Assets}

Plant knowledge is stored as structured JSON in \texttt{src/data/plants.json}.
Each plant record contains identifiers, display names, aliases, descriptions,
attributes, and optional information such as medicinal value, toxicity, or
drought tolerance. Scene metadata is stored in \texttt{src/data/scenes.json},
while intent parsing rules are implemented in the client and server parser
modules.

Visual assets are kept in the \texttt{public/} directory:

\begin{itemize}
    \item panoramic scene images;
    \item 3D plant models in \texttt{.glb} format;
    \item UI assets.
\end{itemize}

This separation keeps the prototype extensible. New plants can be added by
combining a plant data record, a model asset, and scene placement metadata,
without changing the main interaction code.

\section{Code Repository}

The source code of the prototype is available in the project GitHub repository:

\begin{quote}
\texttt{https://github.com/Shiqi-H/MITA}
\end{quote}

To run the prototype locally, the required dependencies should first be installed from the project root:

\begin{quote}
\texttt{npm install}
\end{quote}

The frontend and backend must then be started in two separate terminal windows. The frontend can be launched with:

\begin{quote}
\texttt{npm.cmd run dev}
\end{quote}

The backend server can be launched from another terminal with:

\begin{quote}
\texttt{npm.cmd run server}
\end{quote}

After both processes are running, the prototype can be accessed from a web
browser through the local development URL printed by Vite in the frontend
terminal, usually:

\begin{quote}
\texttt{http://localhost:5173/}
\end{quote}

If a different port is shown in the terminal, the user should open that printed
local URL instead. Vite's development server listens on \texttt{localhost} by
default, and \texttt{localhost} is allowed as a development host by default.
